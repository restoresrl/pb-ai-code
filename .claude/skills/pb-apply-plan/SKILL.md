# Applying a `/pb-review` plan to the workspace

This skill is the **Phase B** of the `/pb-review` flow. It consumes
the plan file that `/pb-review` produced and walks the queue voce-by-
voce, applying each fix to the PB workspace through a controlled
loop. Each step is gated by user confirmation; nothing is applied
silently.

It is **not** an orchestrator of code review (that is `/pb-review`).
It is **not** a low-level editor (that is `pb-workflow` in
`pb-orca-mcp`). It sits in the middle: parses the plan, decides the
order, walks the queue, and delegates each edit downstream.

## When to invoke this skill

- `/pb-review` finishes Step 4 and hands off explicitly.
- The user re-opens a previously generated plan file
  (`.pb-review/<...>.md`) in a later session and wants to continue
  applying it.
- The user wants to resume after a partial run (some `status:
  applied`, some still `pending` or `skipped`).

If there is **no plan file yet**, this skill is the wrong choice —
run `/pb-review` first.

## Pre-flight

- ORCA session must be open (`pb_session_open`) with the right
  application set and library list configured. See the sibling
  [`pb-workflow`](../../../../pb-orca-mcp/.claude/skills/pb-workflow/SKILL.md)
  skill for the bring-up recipe.
- The plan file's `target` header must match the currently
  configured target. If they disagree, stop and ask the user to
  reconcile.

## Step 1 — Parse the plan file

Read the plan-file at the path passed in (or, if no path was
passed, ask the user). For every section that starts with
`### fix-NN`, extract the fenced ```yaml block immediately under
the heading.

Required YAML fields (per `/pb-review` contract):

- `id` — unique identifier of the fix (`fix-01`, `fix-02`, ...).
- `entry` — entry triple `lib::name:type`.
- `kind` — `bug-risk` | `refactor` | `style` | ...
- `priority` — `high` | `medium` | `low`.
- `depends_on` — list of `id`s that must be applied first.
- `confidence` — `parsed` | `user-augmented` | `manual`.
- `status` — `pending` | `applied` | `skipped`.

Optional: `function`, `lines`, `effort_estimate`, `tag`.

Also extract the **body markdown** for each fix (Where, Why,
Suggested fix code block, Notes). The Suggested fix code block
inside a ```pb fence is the proposed patch.

### YAML invalid handling

If a YAML block fails to parse, **fail explicitly**: report the
section id and the parse error, do not skip silently. The user can
then fix the plan file and rerun this skill. No fuzzy recovery.

## Step 2 — Build the dependency DAG and topo-sort

Construct a directed graph where each node is a `fix-NN` and each
edge `B → A` means "A must be applied before B" (i.e. `B.depends_on`
includes `A`).

Topo-sort with two tie-breaking rules:

1. **Inheritance order**: if two fixes touch entries in the same
   inheritance chain, the ancestor's fix goes first. (Determine
   ancestry via `pb_object_query_hierarchy` if not already in the
   plan's context pack.)
2. **Call-graph order**: if A's entry is a callee of B's entry
   (per the `outgoing_refs` produced by `pb-context-build` v1.1),
   A goes before B.
3. **Priority**: among nodes that are topologically equivalent,
   apply `bug-risk` before `refactor` before `style`.

### Cycle detection

If the DAG has a cycle, the topo-sort is impossible. Surface the
cycle explicitly:

> "Ho rilevato un ciclo nelle dipendenze: fix-03 → fix-05 → fix-03.
> Topo-sort non possibile. Come vuoi spezzare il ciclo?
>
> 1. Forza un ordine manuale (dimmi tu quale fix va prima).
> 2. Rimuovi una delle dipendenze dichiarate (probabilmente
>    sovra-dichiarata)."

Wait for the user to choose; do not guess.

## Step 3 — Confirm the run plan with the user

Before touching any file, present the topo-sorted queue and the
overall plan:

> "Ho ordinato la coda così:
>
> 1. fix-01 — Null deref in `n_logger::flush()` (bug-risk, high)
> 2. fix-04 — Extract base class `n_log_target` (refactor, medium)
> 3. fix-02 — ... (refactor, medium, depends on fix-04)
> 4. ...
>
> Procedo voce per voce con conferma su ogni fix?"

Wait for an explicit OK. This is the **handoff gate** mentioned in
`/pb-review` Step 4.

## Step 4 — The apply loop

For each fix in topo-sorted order **whose `status` is `pending`**:

### (a) Present the diff

Read the current source of the target entry via
`pb_library_entry_export` (do not trust the source captured in the
plan-file's context pack — the file on disk is the truth). Compute
a unified diff between current source and the patched source
implied by the Suggested fix from the plan body.

Show to the user:

```
fix-01 — Null deref in `n_logger::flush()` on empty buffer
Entry: rstpb_core.pbl :: n_logger : userobject, function flush

--- current
+++ proposed
@@ -42,6 +42,7 @@
 protected function long flush()
     long ll_written
+    if IsNull(buf) or Len(buf) = 0 then return 0
     ll_written = ...
```

Ask: "Applico questo fix?".

### (b) On user OK

Invoke
[`pb-workflow`](../../../../pb-orca-mcp/.claude/skills/pb-workflow/SKILL.md)
(sibling `pb-orca-mcp`) for the edit-encoding loop:

1. Export current source.
2. Apply the patch.
3. Re-encode to UTF-16 LE BOM + CRLF (required by PB compiler).
4. `pb_compile_entry_import` to write back into the `.pbl`.
5. Capture any compile errors via `pb_get_last_compile_errors`.

If the import succeeds with zero errors → mark the fix as
**applied**. If errors come back → present them to the user, ask
whether to back out (revert to current source), retry with a
revised patch, or accept the error state and continue.

### (c) On user refusal (skip)

Run **skip-with-impact-check**: query the DAG for fixes that
depend on this one (transitively).

- **If no downstream depends on this fix**: skip silently. Update
  the YAML `status: skipped` (preserve user-supplied reason in a
  new `skip_reason:` field if they gave one).
- **If N downstream fixes depend on this one**: enumerate them
  ("salterei anche: fix-05, fix-07 perché dipendono da fix-01") and
  ask:
  1. **Skip a cascata**: mark all downstream as `skipped` too,
     continue with the remaining independent fixes.
  2. **Abort**: stop the apply loop here, leave everything still
     pending as is.

Do not skip downstream silently; the user must acknowledge the
cascade.

### (d) After every status change

1. Rewrite the YAML block of the affected fix(es) with the new
   `status:`.
2. Regenerate the **summary table** at the top of the plan file
   from the up-to-date YAML blocks.
3. Tick (or untick) the `- [ ]` / `- [x]` boxes in `CHANGELOG.md`
   under `[Unreleased]`. A `skipped` fix shows as `- [~]
   skipped: <reason>` (the tilde is a convention; standard
   Markdown renderers ignore it but it's visible in the source).

Persist these changes to disk **immediately**, so a crash mid-loop
leaves the plan file in a recoverable state.

## Step 5 — Wrap up and promote the CHANGELOG entry

When the loop reaches the end (no more `pending` fixes), summarize:

> "Coda completata.
> - Applicati: N
> - Skippati: M (di cui K skip a cascata)
> - Rimasti pending: 0
>
> Vuoi promuovere `[Unreleased]` in `CHANGELOG.md` a una nuova
> versione `[X.Y.Z]` con data odierna? Bump proposto:
> `<patch|minor|major>` (dal plan file)."

If the user confirms:

1. Locate or invoke the local versioning skill (consumer
   `.claude/skills/pb-review-versioning` or `pb-version-local`,
   convention from `/pb-review` Step 0). If present, ask it for
   the next version number using project conventions. If absent,
   compute `X.Y.Z` from the current latest released tag in
   `CHANGELOG.md` plus the proposed bump.
2. Rename `## [Unreleased]` → `## [X.Y.Z] - YYYY-MM-DD` in
   `CHANGELOG.md`.
3. Insert a fresh empty `## [Unreleased]` section above it.
4. If a local version file exists (`.version`, `package.json`,
   etc.), update it accordingly — delegate to the local versioning
   skill if present.

If the user declines, leave `[Unreleased]` as is. The promotion
can happen later, manually or by re-running this skill with a
flag.

## What this skill never does

- **Never applies edits without per-fix confirmation**. Even on
  trivial fixes. The whole point is auditable application.
- **Never edits sections of `CHANGELOG.md` other than the current
  `[Unreleased]`**. Past releases are immutable.
- **Never silently re-runs an `applied` fix**. If you see
  `status: applied`, skip it (it's already done). If the user
  wants to re-apply, they must edit the status back to `pending`
  manually.
- **Never auto-resolves cycles** in the DAG. Always ask the user.
- **Never trusts the plan's context-pack source** as the live
  state. Always re-export from `.pbl` before computing diffs.

## Failure modes to handle gracefully

- **Plan file missing or malformed**: stop, ask user for path or
  to rerun `/pb-review`.
- **Plan target doesn't match current ORCA session**: stop, ask
  user to switch session or pick a different plan.
- **Edit-encoding loop in `pb-workflow` fails** (UTF-16 BOM lost,
  CRLF stripped, etc.): surface the diagnostic, do not retry
  silently. The sibling skill has its own troubleshooting; refer
  to it.
- **Compile errors after import**: do not auto-rollback. Present
  errors to user and ask: revert / retry / accept.
- **CHANGELOG.md modified externally between status updates**:
  detect via timestamp/hash, warn user, ask whether to overwrite
  or merge.

## Boundaries with sibling skills

- [`/pb-review`](../../commands/pb-review.md) — produces the plan
  file this skill consumes.
- [`pb-context-build`](../pb-context-build/SKILL.md) (v1.1) — its
  `outgoing_refs` populate the call-graph the topo-sort relies on.
  If a fix's `confidence: low` (dynamic call), `pb-apply-plan`
  surfaces a warning rather than treating it as a hard edge.
- [`pb-workflow`](../../../../pb-orca-mcp/.claude/skills/pb-workflow/SKILL.md)
  (sibling) — handles the actual edit-encoding + import. Invoked
  per fix in Step 4 (b).
- [`pb-src-format`](../pb-src-format/SKILL.md) — consulted when a
  fix touches an entry type whose on-disk format has variants.
- `pb-review-versioning` / `pb-version-local` (optional, consumer-
  local) — invoked at promotion time in Step 5 to apply project-
  specific versioning conventions.
